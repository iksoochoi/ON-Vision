# 웹 화면 속도 (세트가 많이 쌓여도 느려지지 않게)

저장된 세트(신발 한 번 지나간 묶음)가 수천~수만 개로 늘어도 화면이 느려지지 않도록, **파일을 매번 읽던 것을 메모리 색인으로 바꾸고, 화면이 주기적으로 물어보던 것을 서버가 알려 주는 방식(SSE)으로 바꿨습니다.**

## 무엇이 느렸나 (세트 6,000개, 신발 약 2,000켤레 기준 측정)
| 화면 / 요청 | 하는 일 | 전 | 후 |
|---|---|---|---|
| Live: 상태 (`/api/state`, 캡처마다) | 세트 파일을 전부 읽어 개수를 셈 | **1,100 ms** | **0.8 ms** |
| Browse: 신발 목록 (`/api/shoes`) | 전체 파일을 읽고 사진 파일을 하나씩 확인 | 905 ms, 258 KB | **1.6 ms**, 전송 8.7 KB |
| QR: 일별 통계 (`/api/qr/daily`, 15초마다) | 같음 | 930 ms | **0.9 ms** |
| Live: 최근 세트 (`/api/samples?limit=6`) | 파일 이름을 전부 정렬한 뒤 6개를 읽음 | 42 ms | 1.7 ms |
| 썸네일 한 장 | 그 세트의 JSON을 읽어 경로를 찾음 | 파일 1개 읽기 | 메모리에서 찾음 |
전 값은 세트가 늘수록 **비례해서 커집니다**(6만 개면 10배). 후 값은 세트 수와 거의 상관없습니다. 앱을 시작할 때 색인을 한 번 만드는 시간(6,000개에 약 3초, 그동안 첫 요청이 기다림)만 늘었습니다.

## 바뀐 것
### 1. 메모리 색인 (`backend/storage/shoes.py`)
- 세트마다 요약(신발 ID, 시각, 라벨 상태, 사진 존재 여부, **디스크 용량**, QR 읽기 정보)을 메모리에 둡니다. 시작할 때 한 번 만들고, 저장·라벨·삭제가 일어날 때마다 그 세트만 갱신합니다.
- 개수, 신발 목록, 일별 통계는 색인이 바뀐 뒤 **한 번만 계산해서 재사용**합니다.
- 사람이 폴더에서 직접 지우거나 고친 것은 **2분마다** 백그라운드에서 맞춥니다(`RECONCILE_SEC`). 바뀐 게 있으면 화면에 알립니다.

### 2. SSE로 전환 (`backend/core/events.py`, `backend/api/feeds.py`)
| 화면 | 전 | 후 |
|---|---|---|
| Live | 2.5초마다 `/api/state`, 캡처마다 요청 3번 | **상태는 서버가 2.5초마다 `state` 이벤트로**, 캡처가 저장되면 최근 세트와 개수를 `live_data`로 한 번에 |
| QR | 3초마다 `/api/qr`, 15초마다 `/api/qr/daily` | 처음 한 번만 가져오고, 읽은 코드(`qr`), 카메라별 스캔 상태(`qr_scan`, 2초마다), 통계(`qr_stats`, 세트가 바뀔 때 최대 2초에 한 번)를 서버가 보냄 |
| Browse, Label | 모든 이벤트를 받음 | `samples_changed`만 받음 |
- **필요한 이벤트만 받습니다**: 화면이 `/events?topics=live,qr`처럼 원하는 묶음(`live`, `qr`, `qrpage`, `data`)을 알려 줍니다.
- **아무도 보고 있지 않으면 서버는 아무것도 만들지 않습니다**(구독자가 없으면 상태나 통계를 계산하지 않음).
- 여러 번 연달아 바뀌어도(캡처 한 번에 컷 3개) 화면에는 **한 번만** 보냅니다(0.3초 묶음).
- 연결이 끊겼다 돌아오면 화면이 **한 번 전부 다시 가져옵니다**. 화면이 이벤트를 못 따라가 큐가 넘치면 서버가 `resync`를 보내 같은 일을 시킵니다. 닫힌 화면은 1초 안에 서버가 알아차려 구독에서 뺍니다.
- QR 화면의 "3s ago"는 서버 시각과의 차이를 보정해서 **다른 컴퓨터에서 열어도 맞게** 보이고, 서버에 묻지 않고 화면에서 1초마다 올라갑니다.

### 3. 그 밖의 개선
- **Browse 신발 목록**: 서버가 검색어에 맞는 앞 400켤레만 보내고(`/api/shoes?limit=400&q=...`), 전체 합계(신발, 세트, 사진, 용량)는 따로 줍니다. 화면에 열려 있는 신발은 검색과 상관없이 항상 포함됩니다. 검색은 입력이 멈춘 뒤(0.25초) 서버에서 합니다.
- **압축과 캐시**: 정적 파일(HTML, JS, CSS)은 메모리에 두고 `ETag`로 **바뀌지 않았으면 304**(본문 없음), 큰 JSON과 정적 파일은 gzip(신발 목록 256KB가 23KB로). 사진과 썸네일은 하루 동안 브라우저가 보관합니다(같은 id의 사진은 바뀌지 않음).
- **캡처 로그**: 색인을 만드는 동안에도 저장이 기다리지 않습니다.

## QR 화면의 Size 열 (세트 용량)
일별/시간별 표에 **Size**가 생겼습니다. 그 세트들의 **사진과 썸네일**이 디스크에서 차지하는 용량입니다(JSON은 사진의 0.01% 수준이라 뺐습니다). 숫자에 마우스를 올리면 **세트당 평균**이 나옵니다. 합계 줄은 전체 용량입니다.

## 확인하는 법
```bash
curl -N "http://localhost:8090/events?topics=live"     # 2.5초마다 state 이벤트가 흘러나옴
curl -s "http://localhost:8090/api/qr/daily" | head -c 300
```
브라우저 개발자 도구의 Network에서 Live 화면을 열어 두면, 이제 `/api/state` 요청이 반복되지 않고 `events` 연결 하나만 보입니다.

## 남은 한계
- **Label 화면**(메뉴에서 숨겨 둠)의 목록(`/api/samples?status=...`)은 아직 해당 상태의 **모든 세트를 한 번에** 가져옵니다(`?limit=&offset=`는 서버에 있음). 라벨링을 다시 쓰게 되면 페이지 단위로 바꾸세요.
- Browse에서 **신발 한 켤레의 세트**를 열면 그 신발의 세트 JSON만 읽습니다(한 켤레는 보통 수십 개). 같은 신발이 수천 번 나오는 일은 없어서 그대로 둡니다.
- 서버는 요청마다 새 연결을 맺습니다(HTTP/1.0). 같은 컴퓨터에서 보는 현재 구조에서는 문제가 없습니다.
- 숫자를 바꾸고 싶으면 `backend/api/feeds.py`의 `STATE_PUSH_SEC`(2.5), `QR_SCAN_PUSH_SEC`(2), `STATS_MIN_SEC`(2)입니다.
